# 推断耗时与资源复用

网页端和 `scripts/recognize_glamour.py` 共用同一实现，默认开启资源复用；网页额外使用串行常驻识别进程。无需重新生成图库、索引或模型权重。

## 已实施的优化

- 未微调的查询编码器、样式分类模型及处理器按模型、设备、预处理方式复用，命令行最多保留两组，网页常驻进程最多保留八组；微调的 DINO 查询模型仍独立加载，避免把某一部位的权重用于其他部位。
- 索引元数据、只读向量映射及候选图片原始字节在本次任务内复用。缓存按路径、文件大小、修改时间、创建时间和文件标识区分；文件发生变化时重新读取。图片内容哈希、原有特征缓存键及验证逻辑不变。
- 文件缓存采用有限容量的准入策略：满后保留已经进入缓存的文件，后续文件直接读取。这样，多次顺序扫描大图库时不会出现每次访问前都刚好淘汰旧条目的问题。容量记账上限为 256 MiB，JSON 元数据按磁盘体积的十倍估算，向量使用只读内存映射；这不是整个进程的内存上限。
- 同一候选路由的向量矩阵只选择、复制一次，供多个裁剪使用；CUDA 端也只传输一次。不改变矩阵乘法、浮点精度、阈值、融合权重或候选排序方法。
- 减少阶段之间强制执行的完整垃圾回收和 CUDA 分配器清空。命令行任务结束清除复用引用；网页保留冻结模型供下一次任务使用，文件与索引缓存仍在每次任务结束时释放。

## 查看耗时

每份识别输出增加 `performance.json`，`results.json` 同时包含 `performance` 字段。日志输出 `TIMING` 阶段记录和 `PERFORMANCE` 汇总，网页任务显示总耗时及各部位耗时。

- `elapsed_seconds`：从参数解析后开始，到报告导出结束的墙钟时间，不包含 Python 启动和模块导入。
- `stages.*.seconds`：包含子阶段的耗时，不能直接相加。例如头部耗时包含模型加载、局部特征读取与检索。
- `stages.*.self_seconds`：扣除被计时子阶段后的自身耗时。
- `cache`：实际模型加载/命中、图片读取/命中以及索引读取/命中次数。

计时保持原有执行顺序；编码和检索返回 CPU 结果时已完成相应设备计算。没有为了计时在每个操作后额外强制同步 GPU。

## 复现与回退

在同一环境中用同一图片、同一参数顺序运行，避免并行运行其他推断干扰耗时：

```powershell
python scripts/recognize_glamour.py <图片> --device cuda --top-k 20 --output-dir data/outputs/perf-cached
python scripts/recognize_glamour.py <图片> --device cuda --top-k 20 --no-runtime-cache --output-dir data/outputs/perf-uncached
python scripts/compare_inference_reports.py data/outputs/perf-uncached/results.json data/outputs/perf-cached/results.json
```

CPU 测试将 `--device cuda` 改为 `--device cpu`。`--no-runtime-cache` 关闭模型、文件复用及合并特征缓存读取，并恢复阶段间内存清理，保留计时与候选矩阵的重复复制修复，因此不等同于所有代码均回到旧版本。

默认复用会增加任务运行期间的内存/显存占用；资源紧张时可使用上述关闭开关。网页默认保留识别进程和模型，持续占用一定内存/显存；切换 CPU/GPU、执行图库任务、任务失败或关闭服务时释放，模型资产变化时清空模型池。设置环境变量 `PRISM_ONESHOT=1` 后启动网页可恢复每次任务独立进程。操作系统文件缓存、杀毒扫描、磁盘和报告导出会影响总耗时，应同时查看阶段数据并进行多次测试，不能把一次样本的收益视为所有输入的保证。

## 2026-10-11 本机验证

同一张 `data/outputs/web/a27aa841855e/input/source.png`，五个部位，`top-k=20`、`candidate-k=1000`、默认批量 16。使用同一 Python 3.12 环境和同一图库；旧版为已发布 beta.5 的代码。以下均在正常权限环境顺序运行，包含进程启动及成功的 PNG 报告导出：

| 设备 | 旧版 | 优化后 | 耗时减少 |
| --- | ---: | ---: | ---: |
| CPU | 78.0 秒 | 51.0 秒 | 34.6% |
| RTX 5070 Ti / CUDA | 57.4 秒 | 42.5 秒 | 26.0% |

这是单样本测量，不是整个数据集的性能保证。早期沙箱测试因文件访问开销和 PNG 导出受限，没有用于上表。

- 四次运行的五部位前 20 候选身份和顺序完全一致；39 张 PNG 裁剪逐字节一致。

- 一次任务中，17 次可复用模型请求实际加载 8 次、命中 9 次；候选图片读取命中 2540 次。
- 610 项回归测试通过；`recognize_glamour.py --check` 资产检查通过；网页 JavaScript 语法检查通过。

## 2026-10-11 第二轮：常驻模型与合并局部特征缓存

网页通过 JSON 行协议把任务交给串行常驻子进程，日志和耗时继续实时显示。每次任务的统计、文件缓存和报告独立；仅冻结模型跨任务保留，微调模型不进入共享池。冻结模型及默认姿态模型的权重/配置文件变化时清空共享模型和资产签名；图库任务开始前终止常驻进程。失败进程不再复用，下一任务重新启动。

头部几何、眼部向量和覆盖分类的小文件建立可丢弃的 SQLite 合并缓存，放在用户缓存的 `feature-packs-v1` 下。首次读取填充，后续按批查询。原文件仍是依据，每次核对文件大小、修改/创建时间和文件标识，修改或删除会失效。图片内容哈希、特征键、数组数值验证、FP32 计算和排序逻辑保持不变。合并库不可用时回退原文件；无需重建图库。

同一截图、RTX 5070 Ti、五部位、top-k=20，顺序运行并成功导出 PNG：

| 运行方式 | 端到端耗时 | 可复用模型加载 / 命中 |
| --- | ---: | ---: |
| 独立进程，本轮合并缓存首次填充 | 42.6 秒 | 8 / 9 |
| 常驻进程首次任务，合并缓存已有 | 35.2 秒 | 4 / 13 |
| 同一常驻进程第二次任务 | 26.6 秒 | 0 / 17 |

第二次比本轮独立进程减少约 37.7%，约快 1.60 倍；相对上一轮 42.5 秒减少约 37.5%。首次常驻任务这次已命中合并库，不能将 35.2 秒视为全新安装冷启动结果。单张截图测量包含系统文件缓存和模型库初始化的影响，不代表所有输入。

- 合并读取命中 30,704 项，读取阶段约 0.64 秒；首次填充约 2.20 秒。
- 头部局部证据从上一轮约 12.81 秒降至本次热任务 7.42 秒（阶段有嵌套）。
- 与上一轮 GPU 报告及本轮独立进程对照，五部位前 20 候选身份、排序和分数完全一致；39 张裁剪 PNG 逐字节一致。
- 613 项全量回归通过，随后补充的两项进程协议测试也通过（总计 615 项）。
- 测量记录：`work/persistent-performance.json`；一致性记录：`work/persistent-parity.json`；可复现脚本：`work/benchmark-persistent.py`。

重启网页服务后生效。释放常驻模型显存可关闭服务，或使用 `PRISM_ONESHOT=1` 启动。合并缓存可以删除，后续识别自动填充。
