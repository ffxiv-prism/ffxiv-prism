## beta.5：CPU / CUDA 一致性修复

用户指出 CPU / CUDA 名次不同后，补做了同环境对照。未修复时：开发 CUDA 帽子第 6、鞋第 7；开发 CPU 第 5、第 7；便携 CPU 第 8、第 13。此前将开发 CUDA 与便携 CPU 直接当成设备差异不够严谨。

根因分为四层：

1. 便携环境缺少 torchvision，SigLIP 的 AutoProcessor 自动选择 `SiglipImageProcessorPil`；开发环境选择 `SiglipImageProcessor`。
2. 两边 Pillow 均为 11.1.0，但开发 Conda 使用 libjpeg 9，便携 wheel 使用 libjpeg-turbo 3.1.0；推断裁剪保存成 JPEG，产生不同的二次压缩和解码像素。
3. 姿态估计的细小设备误差使头部两个裁剪左边界相差 1 像素。
4. 即使张量是 FP32，CUDA 的 cuDNN 卷积默认仍允许 TF32。对相同 PNG 裁剪，DINO 查询向量差异约 1e-4，足以被排名融合放大；SigLIP 对照仅约 1e-7。另有仅 CUDA 样式分类开启 FP16 的不一致。

beta.5 锁定相同依赖版本和 Windows Pillow wheel，补入 CPU torchvision，明确指定同一处理器后端；姿态使用 CPU，识别裁剪保存 PNG；查询推断使用 IEEE FP32，并明确关闭 CUDA 矩阵与 cuDNN 卷积 TF32。全局和局部检索采用同一六位小数稳定并列约定。查询分类缓存包含新推断契约，已发布候选特征维持同一份固定输入。

三套实际运行（开发 CPU、开发 CUDA、便携 Python 的新 CPU 环境）得到完全相同的 39 张 PNG 裁剪，以及五部位每部位前 20 个候选身份和顺序。帽子第 4、说教筒靴第 13；这是新无损裁剪流程的结果，与 beta.4 的 JPEG 流程不应混比。CPU/GPU 浮点分数不要求逐位相等，不承诺任意输入、任意硬件都必然获得逐位相同结果。

完整测试 602 项通过。对应报告为 `data/outputs/validation-20261010-ieee-cpu/`、`validation-20261010-ieee-cuda/` 和 `validation-20261010-portable-parity/`；环境安装与复验方法见 `docs/runtime_parity_zh.md`。beta.5 继续使用已完整验签的 `gallery-20261009-visor-feet-v3`，无需再次下载该图库。
